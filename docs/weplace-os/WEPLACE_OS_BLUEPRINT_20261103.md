## 1. 제품을 세 표면으로 나눈다

### A. 공개 홈페이지 — Discover / Trust / Ask
- 메인 R2의 **매출 사례 → 화면의 변화 → 검색·AI → 실제 근거 → FLOW 소개 → 첫 진단**의 간결한 이야기 보존.
- HERO의 수치는 기록 기준이 있는 현재 값만 사용. 매출 상승 기여도와 보장을 주장하지 않는다.
- `#flow`에는 '고객이 무엇을 확인하는가'와 '직원이 어떻게 검수하는가' 두 개의 **비식별 예시 장면**을 제시한다.
- 메인에 내부 CRM 패널·직원 KPI·로그인 폼을 직접 삽입하지 않는다. 상단에는 '내 매장 확인' 정도의 단일 유틸리티 링크, 직원 진입은 푸터/전용 로그인 동선에서 제공.
- 제안 경로: `/how-we-work/` (운영 방식·승인 방식 공개), `/my-store/` (고객 입구, 기존), `/team` (직원 입구, 기존 리디렉트).
- 메인 버튼은 '진단 받아보기', '고객 작업실 보기'의 역할을 혼합하지 않는다. 진단 문의를 고객 로그인으로 오인하지 않도록 분리한다.

### B. 직원 FLOW — Operate / Review / Learn
- 기존 `flow_prospects`, `operations.accounts/events`, `flow_briefs`, `flow_client_grants`, `flow_client_records`, 공개 저널 체계를 중심으로 사용.
- 내부 사람의 사용 흐름: **오늘의 FLOW** (우선순위 상위 3개) → **팀의 흐름** (매장별 진행·담당·납기·리뷰 대기) → **매장 작업 상세** (계약 범위, 근거, 작업, 검수, 고객 공유, 다음 회차).
- '업무 관리자 / 영업 / 담당자 / 검수자'는 화면에서의 책임 분담이지 기존 데이터베이스 `flow_memberships.role`의 신규 enum 값이 아니다. 실제 역할 값은 owner/member. 추가 접근 권한은 서버에서 검증해야 한다.
- Google Sheets와 Drive, Calendar, 제안서 HTML, 디자인 툴은 초기에 **승인된 링크·첨부·import**로 묶는다. 서로 독립된 '진실' DB를 만들지 않는다.
- 계약 입력은 계약 증빙과 상품 범위 검토에만 사용한다. 임의의 GPT 추출 결과가 서명된 계약이나 납품 완료 상태가 되면 안 된다.

### C. 고객 FLOW — See / Ask / Approve
고객에게 남기는 1개 화면:
1. 이번에 완료한 일과 실제 변경 전/후 증빙
2. 현재 진행 상태 및 다음 공유 예정 작업
3. 지금 고객이 확인해야 하는 **최우선 1건**
4. '승인' 또는 '수정 요청' (이유 기록)
5. 계약에 포함된 범위·포함되지 않은 별도 견적의 구분

고객은 본인 계정의 active `flow_client_grants` 및 명시적으로 공유된 결과만 조회한다. 직원 메모, Prospect 자료, 다른 거래처, 내부 금융 데이터는 절대 노출하지 않는다.

## 2. 하나의 실제 흐름 — 상태값과 인간 증빙을 섞지 않는다
| 순서 | 사용자에게 보이는 단계 | 기존 객체 / 증빙 | 진행 책임 | 비고 |
|---|---|---|---|---|
| 01 | 문의 | 고객의 실제 전송 확인 → Prospect | 영업 담당 | 버튼 클릭 ≠ 접수 |
| 02 | 현장 진단·미팅 | `operations.events`, 확인한 채널·질문 | 영업/전략 | 예정 ≠ 참석 |
| 03 | 제안 | `flow_briefs` 버전·근거 상태 | 전략/승인자 | 견적 ≠ 계약 |
| 04 | 계약·착수 | `operations.accounts.contractStatus`와 별도 결제 증빙 | 책임자 | 메모 ≠ PG 성공 |
| 05 | 프로젝트·업무 | 계약 범위별 내부 작업, 담당·날짜·증거 | 운영자/실행자 | 계약 외 작업 표시 |
| 06 | 별도 검수 | 지정된 검수자 확인·재작업 | 검수자 | 작성자가 자기 검수 불가 |
| 07 | 고객 공유·승인 | active grant, 공유 작업, 승인/수정 요청 | 운영/고객 | 새로운 수정 회차, 기존 승인본 보존 |
| 08 | 정기 보고·재계약 | 변화의 근거·범위·담당·반응 | 전략/영업 | 성과 인과관계 단정 금지 |
| 09 | 승인된 사례 공개 | `published` 공개 projection | 공개 승인자 | 고객별 공개 동의 별도 |

'진행률'은 초기에는 **확인된 납품 건수**와 **계약 이행률 미집계**를 구분한다. 실제 계약별 작업 가중치·인수 기준이 승인되기 전 45% → 60%와 같은 수치를 임의 생성하지 않는다.

## 3. 직원 내부 툴 허브 — 한 번에 전부 만들지 않는다
| 모듈 | 1차 경험 | 저장 기준 |
|---|---|---|
| CRM | 신규·관심·제안중, 다음 연락, 상담 근거 | 기존 FLOW prospects |
| Contracts | 실제 계약서, 범위, VAT, 계약기간, 변경 이력 | 기존 accounts + 원본 문서 |
| Workroom | 매장·담당자·납기·증빙·검수 | FLOW 기존 work/request 체계 |
| Proposal OS | 브리프·제안 버전·고객 선택지 | 기존 briefs, CONFIRMED/VERIFY/HYPOTHESIS |
| Content/Asset Shelf | 사진, FAQ, 브랜드 정보, 공유 가능 파일 | 권한 있는 저장소 링크와 메타데이터 |
| Client Portal | 승인 대기와 고객에게 공개한 결과물 | grant 기반 projection |
| Report & Renewal | 기간별 활동/성과 근거, 갱신 예상 | 별도 계약/수치 검증 후 |
| Ledger / Finance | 내부 독립 서비스로 deep link부터 | 고객 영역·일반 직원 영역과 격리 |

디자인 원칙: 직원 화면은 **실행을 위한 밀도**, 고객 화면은 **안심을 위한 간결함**, 메인 홈페이지는 **진입을 위한 설득 없는 증거**.

## 4. 데이터·보안 불변조건
- 공개 홈페이지에서 기존 인증된 FLOW `prospects`/작업 API를 직접 호출하지 않는다.
- 신규 리드 자동 수집은 별도 동의 문구, 수집 최소화, 보유·삭제 기준, 입력 검증, 중복, 스팸, 속도 제한, 관리 권한, 감사 기록, 테스트를 먼저 완료한다.
- 고객 권한은 staff membership과 별도; grant 승인·회수·다른 고객사 격리를 서버에서 검사한다.
- 고객 공유 검수와 **외부 공개 동의**는 독립된 승인이다.
- 로그/분석에도 고객 이름, 내부 UUID, 계약 내용, 진단 답변, 토큰을 전달하지 않는다.
- FLOW 파일럿은 실 운영 Netlify Identity·Database·Blobs와 **물리적 또는 논리적으로 검증된 격리**가 필요하다. Preview가 안전한 격리라는 가정 금지.
- 최신 PR 계보 및 기존 redirect, 정책, 키워드·실적 근거, 모바일, 접근성 보존.

## 5. 권장 실행 순서
### P0 · 운영 공개 준비
- R2 PR #13의 실제 링크·버전·콘텐츠 승인.
- 회사 증빙과 개인정보 처리방침의 실무 운영 확인; production build 게이트 통과.
- 수치·이미지·동의, 회사 표기, 카카오 CTA, 모바일/성능, 롤백 검증.
- 다른 기능 출시와 분리하여 R2 운영 공개.

### P1 · FLOW 업무 연결 (기존 도메인에서)
- 최신 FLOW Draft #18/#19 기능과 현 운영 deploy의 정확한 차이를 확인한다.
- 직원 2역할 + 고객 2계정의 격리된 E2E: 작업 → 지정 검수 → 고객 공유 → 승인·수정.
- 기존 /team, /client 진입 경로와 고객 연결 SOP를 안정화한다.
- 계약서·Google Sheet/Drive/Calendar는 읽기·deep link부터 시작한다.

### P2 · 홈페이지 → CRM 연결
- 신규 문의 최소 필드와 별도 개인정보 동의.
- 인증된 내부 intake adapter, idempotency, 작업 배정 통지, 중복·오류 큐.
- 리드 도착을 성과로 보지 않고 **담당자 수신·확인 기록**을 기준으로 운영.

### P3 · 리포트·업셀링·지적 자산
- 월별 '한 일 / 달라진 화면 / 확인한 결과 / 아직 모르는 것 / 다음 한 가지' 보고.
- 재계약·추가상품은 계약 범위와 현장 질문에 근거한 **제안 후보**, 자동 청구 금지.
- 현장 반응을 익명화한 체크리스트, SOP, Case Study 및 Mashcore 연구 메모로 축적 (법적/계약상 공유 범위 내).

## 6. 검수 기준 (Release Acceptance)
- 공개 홈페이지: 모바일 320~1440px, 키보드, reduced-motion, 이미지 실패, JS 차단, SEO/OG, 폼 실제 미전송 안내, 메타/수치 검증.
- staff: 임의 직원이 다른 owner 업무를 수정하지 못함, 독립 검수, 충돌(409), 실패 후 입력 보존, 감사 기록.
- client: active grant 없을 때 404/제한, 다른 매장 정보 0건, 공유 이전 자료 0건, 수정 시 기존 승인 결과 보존.
- intake: 허가 전 **완전 비활성**, 동의 없는 전송 불가, 중복 방지, 취소·삭제·철회 정책.
- production: 회사·개인정보 승인 데이터 통과 + 점검된 배포 commit/rollback. 승인 게이트 우회 금지.
